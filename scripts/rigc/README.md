# rigc — the rig transpiler

A **rig** is a named topology: one board, plus the shields plugged into
its typed sockets, plus how they are configured. `rigc` compiles that
description into the devicetree overlay a Zephyr build consumes, and
refuses the ones that cannot physically work — a shield that needs SPI on
a socket exposing none, two devices claiming one chip-select, a required
parameter left unassigned.

This directory is the tool, its tests, and its gate. **It is not yet
wired into the build**: no CMake, no west command, no documentation. Those
follow separately. What it *can* do today is run standalone and hand you
an overlay, which is enough to be useful and enough to judge the tool by.

## What works today

The command below runs against the fixture data that ships with the test
suite — the only board and shield definitions in this change — and is the
whole flow end to end. From the repository root:

```console
$ export ZEPHYR_BASE=<your zephyr tree>
$ export PYTHONPATH=scripts
$ F=scripts/rigc/tests/fixtures

$ python3 -m rigc expand \
    --promote 'fixture_logger:socket=fixture_socket_a' \
    --board reference_board \
    --board-dts    $F/boards/mainboards/board.dts \
    --shield-dir   $F/boards/rigs/reference-shields/shields \
    --connector-dir $F/dts/connectors \
    --bindings-dir  $F/dts/connectors \
    --include-dir   $F/include \
    --out-dir /tmp/rig-out
$ echo $?
0
```

`--promote` is the no-rig-file case: name a shield and rigc synthesizes
the one-instance rig around it. A real rig with several shields is the
positional form instead — same flags, a `rig.yml` path in place of
`--promote`:

```console
$ python3 -m rigc expand \
    $F/boards/rigs/reference-shields/rig.yml \
    --board reference_board \
    ...
```

### What comes out

`/tmp/rig-out/rig-gen.overlay` is the artifact you want:

```dts
/* generated by rigc — do not edit; the rig file is the source of truth
 * rig: fixture_logger  board: reference_board
 */

&fixture_i2c {
	fixture_logger_fl_sensor: sensor@50 {
		compatible = "vnd,fixture-sensor";
		reg = <0x50>;
		status = "okay";
	};
};

&fixture_spi {
	cs-gpios = <&fixture_socket_a 4 1 /* ACTIVE_LOW */>;
	fixture_logger_fl_flash: flash@0 {
		compatible = "vnd,fixture-flash";
		spi-max-frequency = <8000000>;
		reg = <0>;
		status = "okay";
	};
};
```

Note what rigc resolved rather than copied: the chip-select GPIO, the CS
index, the I2C address, the socket a shield-local pin name maps to. The
shield template says *"my flash sits on the socket's SPI"*; the board says
which controller that socket's SPI is; rigc joins them.

Three more files land beside it:

| file | what it is |
|---|---|
| `config-sheet.md` | the human-readable half: socket assignment, chip-selects and resolved parameters per instance — what you hand whoever wires the hardware |
| `expectations.yml` | a machine-readable stub of what a runtime harness should observe: device X answers on bus Y at address Z |
| `context.cmake` | the rig's identity and its dependency list, for a build system to consume |

A `rigc-generated/` working directory is kept beside them on **every**
exit, success or failure: the preprocessed board and shield devicetree,
and for `--promote` the synthesized `rig.yml` pair. When a diagnostic
names a line, that is the file it means.

### Wiring the overlay into a build

Today, by hand:

```console
$ cp /tmp/rig-out/rig-gen.overlay app.overlay
$ west build -b <board> <app>
```

or without copying:

```console
$ west build -b <board> <app> -- \
      -DEXTRA_DTC_OVERLAY_FILE=/tmp/rig-out/rig-gen.overlay
```

## Using it against your own board

Two things are needed, and neither ships here:

1. **A rig-enabled board.** rigc reads the board's own `.dts` and looks
   for typed socket nodes — `compatible = "socket,arduino-r3"` and the
   like. A board with none is reported as *"it exists, but is not
   rig-enabled"*. Opting a board in is a devicetree change to that board.
2. **A connector-type root.** The `socket,*` bindings and the
   position-index headers they reference. `--connector-dir` points at the
   bindings, `--include-dir` at the headers.

`--bindings-dir` is the ordinary edtlib bindings search path used to read
the board; you will usually need your connector root **and** `$ZEPHYR_BASE/dts/bindings`
on it, since the socket bindings `include:` Zephyr's own `gpio-nexus.yaml`.

## What is missing, and why it matters

Look again at that command. Seven path flags, every one of them a fact the
build system already knows: which board, where its `.dts` is, the bindings
search path, the cpp include path. Omitting one is refused rather than
guessed — leave out `--connector-dir` and you get

```
error[lang-connector-root]: no --connector-dir was given and the built-in
fallback (.../dts/bindings/connectors) does not exist -- that fallback is a
dev/test convenience, not the production path
```

which is the right behaviour and still seven things a human has to get
right by hand, every time.

**That flag list is the argument for the build-system integration.** Under
CMake none of it is typed: the board and its devicetree come from the
build, the bindings and include paths are the ones the build already
computed, the overlay is generated into the build directory and applied in
the same configure step, and `context.cmake`'s dependency list makes the
whole thing re-run when a rig file or shield template changes. A rig
becomes `-DRIG=<name>` on an ordinary `west build`.

Standalone operation stays supported and is what the test suite drives —
but it is the seam for tooling, not the way anyone should have to build a
rig by hand.

## Running the tests

```console
$ ZEPHYR_BASE=<your zephyr tree> scripts/rigc/check.sh
```

mypy over the package, the unit suite under a coverage floor, then the
integration suite driving the real CLI as a subprocess. `CHECK_FAST=1`
deselects tests marked `build`; this suite carries none yet.

The suite is hermetic: it reads only the vendored fixtures under
`tests/fixtures/` and threads them explicitly on every call, never through
the module-relative fallbacks mentioned above.
`tests/integration/harness.py`'s `assert_fixture_local` is the structural
proof of that, applied per test.

**One limit worth stating plainly:** every build-reaching test — the ones
that configure a real board with a real toolchain and compare the result —
is tethered to real boards and rigs, and those live in the repository this
tool came from. So this suite proves rigc is correct in isolation. It does
not yet prove it configures a real board *here*. A rig defined in this
repository is what closes that.

## Layout

| path | |
|---|---|
| `loader/` | rig files and shield templates in, a topology out |
| `board/` | reads the board's real devicetree (edtlib) for its sockets |
| `analyzer/` | resolves it against the board: sockets, addresses, chip-selects, GPIO nets, wires |
| `emitter/` | renders the artifacts; decides nothing |
| `cli.py` | the argv surface; `python -m rigc expand` |
| `tests/` | `unit/` in-process, `integration/` through the CLI front door |
| `check.sh` | the gate |
